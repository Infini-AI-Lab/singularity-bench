# midtrain-for-rl

The mid-training task of Singularity-Bench: mid-train a base model so that it gains as much as
possible from a fixed reinforcement-learning (RL) stage. Every submitted checkpoint receives the same
five-hour GRPO stage, and the score is the model's mean accuracy on math, coding and science
benchmarks after that stage.

**Human baseline: 0.175** (PRISM's Math+Code+Science mixture, trained with Megatron-LM under the same
12-hour limit).

## The task

The agent mid-trains **Llama-3.2-1B-Base** (`meta-llama/Llama-3.2-1B` at revision
`4e20de362430cd3b72f300e6b0f18e50e7166e08`, not the Instruct model) for **12 hours** on one node with
**four NVIDIA GB300 GPUs** and a Grace ARM64 CPU. It receives Megatron-LM without a Hugging Face
checkpoint converter and about 1.1 TB of pinned public corpora (roughly 700B tokens of educational
web text, mathematics, code, reasoning traces and chat, far more than the budget can consume). The
architecture and tokenizer are fixed, and training may use only the provided corpora and the
model's own generations. Data selection, mixture proportions, filtering, formatting, curriculum,
training method (continued pretraining, SFT, RL, merging) and infrastructure are the agent's
choices. The agent's instruction is [`instruction.md`](instruction.md).

After the agent phase, the submitted checkpoint gets the fixed GRPO stage in slime on 43K math,
coding and science prompts, and the resulting model is evaluated on AMC, HumanEval+ and
GPQA-Diamond.

[`data_sources.json`](data_sources.json) pins every model, training-data and development-data
revision.

**Submission.** A complete Hugging Face `LlamaForCausalLM` checkpoint at `/app/out/final_checkpoint`
(the base configuration, exactly the base tensor names and shapes, tied embeddings, finite bf16,
fp16 or fp32 safetensors, no adapters or symlinks), a research log at `/app/RESEARCH_LOG.md`, and
`/app/out/training_dataset.json` naming the processed training data. Graders always use the base
configuration and tokenizer.

**Rules that matter.** Initialize from exactly the provided base model. Train only on the provided
training data (everything under `/app/data` except `dev_evals/`) and on samples generated by the
model being trained; no hand-written examples. Development evaluations are for measurement only.
Do not target evaluation benchmarks or look for grading data, do not change evaluation tools to
alter their results, leave no process running, and do not replace or shadow installed packages.

## Budget and hardware

| Stage | Budget | Hardware |
| --- | --- | --- |
| Agent | 43,200 s (12 hours); at the deadline the agent is stopped and the existing checkpoint is graded | 4 x GB300, 64 GB shared memory |
| Evaluation (RL stage and post-RL evaluation) | 86,400 s; the RL stage itself has an 18,000 s cap | the same 4 x GB300 |
| Verifier and integrity judge | 10,800 s | no GPU |

The budgets and container settings are in [`breakwater.json`](breakwater.json).

## Scoring

1. **Checkpoint check.** A trusted, read-only structural and finite-value inspection
   ([`tests/rl_eval/checkpoint_check.py`](tests/rl_eval/checkpoint_check.py), identical to
   `evals/checkpoint.py`). The RL input combines the base configuration and tokenizer with the
   submitted safetensors; submitted code never runs.
2. **Fixed RL stage.** GRPO in slime for a **five-hour wall-clock budget** (18,000 seconds,
   including initialization, rollouts, updates and checkpoint saves) on a fixed mixture of **43K
   prompts: 19K math, 7K coding and 17K science**. Each step samples 128 prompts with 8 responses
   (1,024 trajectories); inputs are limited to 2,048 tokens and responses to 16,384 tokens. Learning
   rate 5e-7 with linear decay by elapsed wall time, KL (`low_var_kl`, 0.05) to the frozen
   submission, binary rewards: math by symbolic equivalence of the last `\boxed{}` (math-verify),
   code by passing every test of the problem in an isolated CPU sandbox, science by the last boxed
   option letter. The four GPUs are shared by an actor (DP4) and four SGLang rollout engines. The
   latest checkpoint fully saved within the budget is selected; the number of updates depends on
   throughput. The full recipe is in [`tests/rl_eval/README.md`](tests/rl_eval/README.md).
3. **Post-RL evaluation** of the selected checkpoint with slime's evaluation rollouts on SGLang
   (temperature 0.6, top-p 0.95, up to 16,384 generated tokens, 20,480-token context):

| Benchmark | Items | Samples per item | Score |
| --- | ---: | ---: | --- |
| AMC | 83 | 4 | avg@4: mean binary correctness over all 332 responses (symbolic answer check) |
| HumanEval+ | 164 | 1 | fraction of tasks whose response passes the complete expanded test program in the code sandbox |
| GPQA-Diamond | 198 | 1 | accuracy of the last boxed option letter (options shuffled with a fixed seed) |

The task score is the unweighted mean of the three benchmark scores after RL:

```text
score = (AMC avg@4 + HumanEval+ accuracy + GPQA-Diamond accuracy) / 3      (0 to 1, higher is better)
```

The suite shapes are fixed in [`tests/rl_eval/evaluate.py`](tests/rl_eval/evaluate.py) (`EXPECTED`)
and the pinned sources in [`tests/rl_eval/eval_sources.json`](tests/rl_eval/eval_sources.json);
[`tests/grade.py`](tests/grade.py) (`post_rl_reward`) states the acceptance rule.

**Gates.** The reward is 0 when the checkpoint fails the structural check; when RL fails, ends before
its wall-clock stopping window, or leaves no complete checkpoint saved within the budget; when the
evaluation misses any item or sample or is only an integration probe; when the integrity judge does
not return PASS; or when Breakwater detects a rule violation (changed runtime or packages, lingering
processes).

**Human baseline: 0.175**, PRISM's Math+Code+Science mixture trained with Megatron-LM under the same
12-hour limit and scored by the same RL stage and evaluation. The Singularity-Index divides a
submission's score by this value. For reference, the paper also reports a naive uniform mixture,
with an equal token share for each of the 15 datasets (0.117), and the RL stage applied directly to
the base model (0.095).

## Preparing assets

Requirements: a native Linux ARM64 GB300 node with four GPUs, Docker with BuildKit and the NVIDIA
Container Toolkit (with a generated CDI specification), a driver that supports CUDA 13, and
`HF_TOKEN` for an account with access to `meta-llama/Llama-3.2-1B`, `bigcode/starcoderdata` and the
gated GPQA dataset. Preparation streams about 5.8 TB and keeps about 1.1 TB under `data/` and 2.5 GB
under `artifacts/`; agent workspaces need several hundred GB more.

```bash
bash tasks/midtrain-for-rl/prepare.sh --data-only      # base model, corpora and development evaluations
bash tasks/midtrain-for-rl/prepare.sh --images-only    # the images (next section)
bash tasks/midtrain-for-rl/prepare.sh --private-data   # fixed 43K RL mixture and post-RL evaluation sets
bash tasks/midtrain-for-rl/prepare.sh --check          # offline validation (add --deep to rehash everything)
```

A plain `prepare.sh` runs all three preparation steps. Every input is downloaded at a pinned
revision and verified against the repository checksums; each prepared directory gets a completion
record. `prepare_data.py` accepts `--only` and `--limit-files` for testing. The outputs:

| Path (under `tasks/midtrain-for-rl/`) | Contents | Visible to |
| --- | --- | --- |
| `artifacts/Llama-3.2-1B` | the base model and tokenizer | agent (read-only), evaluation, verifier |
| `data/` | corpora and development evaluations | agent (read-only) |
| `private/rl-data/` | `train.jsonl` (43K prompts) and its manifest | evaluation and verifier only |
| `private/eval-data/` | the three benchmark files and their manifest | evaluation and verifier only |
| `.downloads/`, `.tools-venv/` | download staging and the host preparation environment | nobody |

## Building the images

`prepare.sh --images-only` builds, for ARM64, from [`tests/rl_eval/Dockerfile`](tests/rl_eval/Dockerfile)
and [`tests/rl_eval/Dockerfile.sandbox`](tests/rl_eval/Dockerfile.sandbox):

| Image | Contents |
| --- | --- |
| `midtrain-for-rl-agent:local` | the `agent` target: digest-pinned SGLang 0.5.15.post1 / CUDA 13 base, Transformer Engine, Apex, patched Megatron-LM, slime and the training dependencies |
| `midtrain-for-rl:local` | the task runtime image, tagged from the `agent` target by `docker build -t midtrain-for-rl:local tasks/midtrain-for-rl/environment` |
| `midtrain-for-rl-rl:local` | the `rl` target: the same runtime plus `tests/rl_eval` at `/opt/midtrain-rl`, used by `prepare.sh --private-data` |
| `midtrain-code-sandbox:local` | the CPU image in which the code sandbox runs generated code |

After building, `python3 /opt/midtrain-rl/check_runtime.py` inside the runtime image with four GPUs
checks BF16 forward/backward, attention and NCCL. Then build the Breakwater images from the
repository root:

```bash
docker build -f breakwater/author/Dockerfile --build-context task_environment=tasks/midtrain-for-rl/environment \
  --build-arg TASK_BASE=midtrain-for-rl:local --build-arg AUTHOR_CLI=claude-code \
  -t midtrain-for-rl-author:claude-code breakwater
docker build -f breakwater/Dockerfile.verifier --build-context task=tasks/midtrain-for-rl \
  --build-arg TASK_BASE=midtrain-for-rl:local -t midtrain-for-rl-verifier:local breakwater
docker build -t breakwater-observer:local breakwater/collector
docker build -f breakwater/Dockerfile.gateway -t breakwater-author-gateway:local breakwater
```

Use `AUTHOR_CLI=codex` (and a matching tag) for a Codex author image. The evaluation stage runs in
the author image, so the RL stage uses exactly the runtime the agent had.

## Running under Breakwater

**1. Start the code sandbox** on the host. The RL stage's coding rewards and the HumanEval+
evaluation call it; the evaluation container reaches it as `host.docker.internal` (the Docker bridge
gateway, usually `172.17.0.1`), and the agent can never reach it. A non-loopback bind needs a token:

```bash
export MIDTRAIN_CODE_SANDBOX_TOKEN=$(openssl rand -hex 32)
python3 tasks/midtrain-for-rl/tests/rl_eval/sandbox.py --image midtrain-code-sandbox:local \
  --host 172.17.0.1 --port 18081 &
export MIDTRAIN_CODE_SANDBOX_URL=http://host.docker.internal:18081
```

`run.py` refuses to start unless both variables are set, and forwards them only to the evaluation
stage. With `MIDTRAIN_CODE_SANDBOX_URL` set, `prepare.sh --check` also probes the sandbox from a
container.

**2. Bindings.** Copy [`bindings.example.json`](bindings.example.json) and point each `source` at the
prepared input, relative to `--asset-root`. With the default `prepare.sh` layout the asset root is
`tasks/midtrain-for-rl` and the example sources work unchanged:

| Source | Target | Stages |
| --- | --- | --- |
| `artifacts/Llama-3.2-1B` | `/app/models/Llama-3.2-1B` | agent |
| `artifacts/Llama-3.2-1B` | `/private/base-model` | evaluation, verifier |
| `data` | `/app/data` | agent |
| `private/rl-data` | `/private/midtrain-rl-data` | evaluation, verifier |
| `private/eval-data` | `/private/midtrain-eval` | evaluation, verifier |

Targets and stages are fixed by the task contract. `run.py` resolves every source and requires it to
stay under the asset root; if an input is a symlink to another disk, use an asset root that contains
the resolved inputs.

**3. Launch**, with `FIREWORKS_API_KEY` set for the integrity judge and a fresh run directory outside
the task directory and the asset root:

```bash
python3 breakwater/run.py --task tasks/midtrain-for-rl \
  --agent-image midtrain-for-rl-author:claude-code --verifier-image midtrain-for-rl-verifier:local \
  --observer-image breakwater-observer:local --gateway-image breakwater-author-gateway:local \
  --run-dir RUN_DIR --asset-root tasks/midtrain-for-rl --bindings bindings.json \
  --author-cli claude-code --author-model MODEL --author-upstream https://PROVIDER --author-key-env KEY_VAR
```

The task uses GPUs 0 to 3 by default (`--gpus device=0,1,2,3`). Reports land in `RUN_DIR/reports/`
(`mechanical-check.json`, `judge.json`, `reward.json`); the sealed evaluation outputs include the
post-RL `summary.json` with each benchmark score. Generic options and the safeguards are described in
[`breakwater/README.md`](../../breakwater/README.md).

## What the evaluation stage and the verifier do

**Evaluation stage.** After the agent container has stopped and its workspace has been sealed,
Breakwater starts a fresh container from the same image with the sealed workspace read-only at
`/app`. The trusted coordinator (`breakwater/intermediate.py`, kind `midtrain`) checks that the
private evaluation sets match `tests/rl_eval/eval_sources.json`, closes the network except for the
sandbox's address and port (IPv6 to loopback only), and runs `tests/rl_eval/run.sh` on
`/app/out/final_checkpoint` with fresh caches and the four GPUs: checkpoint validation, the RL
mixture check, the five-hour GRPO stage and the post-RL evaluation of the selected checkpoint. RL
checkpoints stay in that container; the receipts, every evaluation response with its reward, and log
tails are sealed. The checkpoint is read as weights only; no submitted code runs. Details:
[`tests/README.md`](tests/README.md).

**Verifier.** A read-only container without GPUs checks the sealed evidence and recomputes the score:
the RL run must have trained on the fixed mixture and pass the completion rule, the evaluated
checkpoint must be the selected RL checkpoint, every suite must have its full shape and data hash,
AMC and GPQA-Diamond rewards are recomputed from the sealed responses, HumanEval+ rewards are taken
as recorded by the sandbox, and the suite scores and the final score must match the recorded ones.
The integrity judge (DeepSeek V4.1 Flash on Fireworks) then reviews the agent's recorded activity,
the sealed workspace and the evaluation outputs against
[`tests/submission_judge.md`](tests/submission_judge.md); processed training data under
`out/processed_dataset` is shown to it as metadata. `reward.json` holds the score only if the verdict
is PASS, and 0 otherwise.

## Tests

```bash
python3 -m unittest discover -s tasks/midtrain-for-rl/tests/rl_eval -p 'test_*.py'   # CPU only; needs PyArrow
bash tasks/midtrain-for-rl/prepare.sh --check                                         # prepared data, images, grading inputs, sandbox
```

The unit tests cover the recipe, timing, checkpoint selection, evaluation, rewards, sandbox routing
and vendor pins. `MIDTRAIN_RUN_DOCKER_TESTS=1` adds a check against the real sandbox image.
